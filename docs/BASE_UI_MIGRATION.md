# React Aria → Base UI migration

Branch: `migration/base-ui-v1.8` · Target: `@base-ui/react@1.8.0` (pinned exactly, no floating range) · Oracle: the
React Aria implementation, frozen in a worktree so migration work cannot corrupt the baseline.

This document is the state of the migration, not an aspiration. Statuses come from
`.design-compiler/base-ui-migration/` (inventory, matrix, per-unit records, captures, reports) and are
regenerated by the commands below.

## Why the shape of this migration is unusual

Three facts discovered by the gates reshaped the plan, and none of them was knowable from prop names:

1. **The Tailwind RAC plugin is the real styling contract.** `registry/untitledui/styles/globals.css` loads
   `tailwindcss-react-aria-components`, whose variants compile to `[data-*]` for elements carrying `data-rac`
   and to *native* pseudo-classes otherwise. After migration no element carries `data-rac`, so `hovered:` /
   `focused:` / `focus-visible:` keep working while `selected:` / `open:` / `pressed:` must be rewritten to the
   attributes Base UI actually emits. `compiler/migration/audit-state-selectors.mjs` lists every variant in
   use and whether its compiled selector can still match.

2. **Base UI has no dates, Table, Tree or Grid.** Proven from the 1.8.0 export surface and the docs index
   (`docs/{calendar,date-field,date-picker,date-range-picker,time-field,table,tree,grid-list}.json` all record
   `exists: false` with evidence). Date controls and Table are therefore `NO_BASE_UI_EQUIVALENT`: reaching zero
   React Aria imports needs an owner-approved native or specialized replacement, not a faked Base UI mapping.

3. **Leaves cannot migrate before their React Aria parents.** React Aria passes wiring through its own context
   and press props: a native-element Button no longer consumes the press props React Aria's `DialogTrigger`
   relies on (the dialog stops opening), and a migrated `Label` cannot name an unmigrated React Aria input
   (axe `label`, critical). Both were caught by the gates and are recorded as dependency edges in the matrix.

## Verification, per change

Nothing here is "it compiles, ship it". Each migrated unit is measured against the frozen React Aria baseline:

| gate | what it proves | command |
| --- | --- | --- |
| parity | widget state (role/checked/disabled), per-step interaction outcomes, portal content, slot geometry (±1px) and computed styles are unchanged | `node compiler/migration/capture.mjs --label migrated && node compiler/migration/parity.mjs --label migrated` |
| accessibility | no **new** axe WCAG A/AA violations versus the baseline (pre-existing debt is reported, never silenced) | `node compiler/migration/a11y.mjs --label candidate` |
| hydration | 43 cases rendered with `renderToString` then hydrated, mismatch-free | `node compiler/migration/hydration.mjs` |
| residue | no React Aria import remains in canonical runtime code | `node compiler/migration/residue.mjs` |
| state selectors | no React Aria state variant left silently dead | `node compiler/migration/audit-state-selectors.mjs` |
| everything | all of the above plus typechecks, SSR, registry consistency, visual canaries, terminal-state check | `pnpm verify:base-ui-migration` |

Captures are recorded from a *pristine* React Aria checkout: `git worktree add /tmp/ds-baseline <commit>` and a
dev server on port 5174, so the oracle cannot drift.

## Final state

Every migration unit reached a terminal state: **23 BASE_UI_VERIFIED**, **2 NO_BASE_UI_EQUIVALENT**
(date-picker, table - see the owner decision below). No unit is MIGRATING, TODO or STAGNATED, and no
canonical runtime file imports React Aria.

| gate | result |
| --- | --- |
| parity (46 cases against the frozen React Aria baseline) | PASS - 0 failures, 77 explanatory notes |
| residue | PASS - 0 accidental files; the 7 date/table files are `ALLOWED_NO_BASE_UI_EQUIVALENT` |
| accessibility (axe WCAG A/AA, 46 cases) | PASS - 0 new violations; 3 pre-existing, inherited from the baseline |
| hydration (SSR then hydrate, 46 cases) | PASS - 0 mismatches |
| typecheck (app, payload, PRO) · invariants · SSR | PASS |

Three defects were found by these gates and fixed with root causes, not symptom patches: the ComboBox popup
never opening (Base UI's `Select.Item` threw inside a ComboBox, because React Aria's `ListBoxItem` served both
collections), the TagSelect popup not closing on Escape, and MultiSelect closing on the first Escape where
React Aria deliberately consumes it twice (clear the query, then clear the selection).

**Date and table components need an owner decision**: Base UI 1.8.0 has no date or table primitive, so the
seven files in those families cannot be expressed in Base UI at all. `OWNER_DECISION-date-and-table.md` states
the evidence, three options (keep React Aria behind a documented allow-list / approve a specialized
dependency / drop them from the Base UI-backed library), and what each option does to the acceptance gates.

## Continuing

```bash
# 1. baseline (once per harness change, from the pristine worktree)
cd /tmp/ds-baseline && node node_modules/vite/bin/vite.js --port 5174
cd - && node compiler/migration/capture.mjs --label baseline --port 5174

# 2. migrate a unit, then prove it
node compiler/migration/capture.mjs --label migrated && node compiler/migration/parity.mjs --label migrated
node compiler/migration/a11y.mjs --label candidate && node compiler/migration/hydration.mjs

# 3. when a unit is green
node compiler/migration/matrix.mjs && node compiler/migration/report.mjs
```

Read before migrating any primitive: `.design-compiler/base-ui-migration/docs/<primitive>.json` — grounded in
the pinned 1.8.0 package and the official docs. Never infer a Base UI API from memory.
